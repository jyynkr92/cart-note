# 목록 유형 표시·목록 순서 바꾸기·항목 누르기 정리

## 왜

실제로 써 보니 네 가지가 불편했다(사용자 피드백, 2026-11-24).

1. 목록을 추가할 때 고르는 "마트/사이트"에서 "사이트"가 무슨 뜻인지 알기 어렵다. 홈의 목록 카드만 봐서는 마트 목록인지 온라인 목록인지 구분되지 않는다.
2. 홈에서 목록 순서를 바꿀 수 없다.
3. 목록 상세 화면 헤더의 뒤로(‹)·메뉴(⋯) 버튼이 작다.
4. 항목 글자를 누르면 편집 창이 열린다. 장보면서는 누르면 바로 완료 표시가 되는 편이 낫다.

## 목표

- "사이트"를 "온라인"으로 바꾼다. 홈의 목록 카드에 마트·온라인 표시를 붙인다.
- 홈에서 목록 카드를 길게 눌러 끌어 순서를 바꾼다. 순서는 그룹(가족) 전체가 같이 쓰고, 다른 사람 화면에도 실시간으로 반영된다.
- 상세 화면 헤더의 뒤로·메뉴 버튼을 아이콘으로 바꾸고 크게 만든다.
- 항목 줄이나 체크박스를 누르면 완료/해제된다. 편집은 줄 오른쪽 연필 아이콘으로 연다.

## 하지 않는 것

- 사람마다 다른 목록 순서. 사용자가 그룹 공통 순서를 골랐다.
- 목록 안 항목의 끌어서 순서 바꾸기.
- "사야할것"(inbox) 옮기기. 지금 설계대로 맨 위에 고정한다.
- DB의 유형 값(`store`/`online`)은 바꾸지 않는다. 화면 글자만 바꾼다.

## 실패로 보는 것

- 순서를 바꿨는데 다시 열거나 다른 기기에서 보면 원래대로 돌아가 있다(저장 실패, 실시간 재조회가 낙관적 순서를 덮음).
- 오프라인에서 바꾼 순서가 재연결 뒤 엉뚱한 목록에 적용되거나 지워진 목록 때문에 실패해 큐가 멈춘다.
- 길게 눌러 끌기가 목록 카드 누르기(상세로 이동)나 화면 스크롤과 충돌한다.
- 항목을 누르는 것만으로 완료되면서, 선택 모드나 스와이프 삭제가 깨진다.

## 방식 (Approaches)

순서 바꾸기 UI만 방식을 골랐다. 나머지는 기존 코드를 고치는 작은 변경이다.

1. **`react-native-reorderable-list` — 선택.** 이미 쓰는 reanimated 4·gesture-handler 위에서 돌고(peer: reanimated ≥3.12, gesture-handler ≥2.12) 최근(2026-11)까지 업데이트됐다. Expo Go에서도 돈다.
2. `react-native-draggable-flatlist` — 많이 쓰이지만 1년 넘게 업데이트가 없어 reanimated 4 호환을 장담할 수 없다.
3. 직접 구현 — 자동 스크롤·띄우기·빈자리 애니메이션을 다 만들어야 해 위험이 크다.

사용자가 1번을 골랐다(2026-11-24). 끄는 방법은 **카드를 길게 눌러 집기**로 정했다(설계자 판단: 카드가 깔끔하고, 홈 카드에는 길게 누르기 동작이 없어 겹치지 않는다).

## 설계

### 1. 마트·온라인 표시

- 목록 추가 시트의 유형 버튼 글자를 `사이트` → `온라인`으로 바꾼다(값은 그대로 `online`).
- `ListCard`: 이름 앞에 작은 아이콘을 붙인다. 마트는 lucide `Store`, 온라인은 `Globe`이고, `text-muted-foreground` 크기 `size-4`로 한다. 아이콘에는 접근성 이름(`마트`/`온라인`)을 단다. inbox에는 붙이지 않는다. 위치 등록 마트의 📍는 그대로 둔다.

```
┌──────────────────────────────────┐
│ 사야할것                  1개 남음 │  ← 고정, 아이콘 없음
├──────────────────────────────────┤
│ 🏪 이마트 📍              3개 남음 │  ← 길게 눌러 끌기
│ 🌐 쿠팡                   0개 남음 │
└──────────────────────────────────┘
```

### 2. 목록 순서 바꾸기

**화면**
- 홈의 `ScrollView`를 `ReorderableList`로 바꾼다. inbox 카드는 목록 머리(header)에, `+ 목록 추가` 버튼과 초대 안내는 꼬리(footer)에 둔다. 그래서 끌 수 있는 것은 inbox가 아닌 목록뿐이다.
- 카드를 길게 누르면 집고, 끌어서 놓으면 순서가 바뀐다. 짧게 누르면 지금처럼 상세로 간다.
- 정렬 기준(`sortLists`)은 그대로다. inbox가 먼저이고, 나머지는 `sort_order` 오름차순, 같으면 생성 순이다.

**저장 (서버)**
- 새 RPC `reorder_lists(p_family_id uuid, p_ids uuid[])`를 마이그레이션 `0011`로 만든다. SECURITY DEFINER에 `search_path=''`이다. 호출자가 그 그룹 멤버인지 확인하고, `p_ids`의 순서대로 그 그룹의 inbox가 아닌 목록들에 `sort_order = 1, 2, 3…`을 한 번에 쓴다.
  - 그룹에 없는 id나 이미 지워진 id는 건너뛴다(오프라인 재생 때 실패해 큐가 멈추지 않게 한다).
  - `p_ids`에 없는 이 그룹의 목록(그사이 다른 사람이 만든 목록)은 뒤에 붙인다. 기존 상대 순서를 유지한다.
  - pgTAP 테스트를 둔다: 멤버만 가능, 다른 그룹 id 무시, 지워진 id 무시, 빠진 목록은 뒤로, inbox 불변.
- 매번 목록 전체 순서를 보내는 이유: 지금 모든 목록의 `sort_order`가 0이라 "두 목록 사이 값" 방식은 첫 이동부터 쓸 수 없다. 그룹 목록 수는 작다(수십 개 이하).

**저장 (앱)**
- `useReorderLists` mutation을 둔다. 기존 목록 mutation과 같은 큐(`QUEUE_SCOPE`)·세션 게이트(`sessionGuarded`)·`withPrepare` 패턴을 따른다. 변수에 `{ familyId, ids }`(놓은 순간의 전체 순서)를 담는다. 낙관적으로 캐시의 `sort_order`를 1..n으로 다시 매긴다. 실패하면 되돌리고 토스트로 알린다.
- 새 목록 만들기는 `sort_order = (지금 최대값) + 1`로 바꿔 맨 아래에 붙는다.
- 다른 가족의 화면은 기존 Realtime 목록 변경 처리(재조회)로 따라온다.
- 반드시 지킬 교훈:
  - `docs/solutions/logic-errors/offline-queue-replay-must-carry-targets-and-reassert-intent.md` — 대상은 변수에 담고, 서버는 그때 조건을 다시 확인한다.
  - `docs/solutions/logic-errors/offline-queue-optimistic-state-clobbered-by-mid-queue-refetch.md` — 큐가 비기 전에 재조회가 낙관적 순서를 덮지 않는다.

### 3. 상세 화면 헤더 아이콘

- `‹` → lucide `ChevronLeft`, `⋯` → lucide `Ellipsis`, 둘 다 `size-6`이다. 버튼 누르는 영역은 최소 44×44pt다. 접근성 이름(`뒤로`, `목록 메뉴`)은 그대로 둔다.

### 4. 항목 누르기

| 동작 | 지금 | 바뀐 뒤 |
|---|---|---|
| 체크박스 누르기 | 완료/해제 | 완료/해제 (같음) |
| 항목 줄(글자) 누르기 | 편집 시트 | 완료/해제 |
| 줄 오른쪽 연필 아이콘 | 없음 | 편집 시트 (접근성 이름 `편집`) |
| 길게 누르기 | 선택 모드 | 같음 |
| 왼쪽으로 밀기 | 삭제 | 같음 |
| 선택 모드에서 누르기 | 선택/해제 | 같음 (연필 아이콘은 선택 모드에서 숨김) |

기존 테스트 중 "항목을 누르면 편집이 열린다"는 의도된 동작 변경이다. 새 동작 기준으로 고친다.

## 세부 결정 (설계자 판단)

빌더 검토 질문은 모두 설계자가 정했다.

1. **놓는 위치와 inbox.** inbox는 `ReorderableList`의 데이터 배열에 넣지 않는다. 그래서 "맨 위에 놓기"는 inbox가 아닌 목록들 가운데 첫 번째라는 뜻이다. inbox 위로는 놓을 수 없다. `onReorder`의 from/to는 데이터 배열(inbox 제외) 기준 인덱스이다.
2. **새 목록 순서.** `createList`는 `withPrepare` 단계에서 캐시를 보고 `sort_order = (inbox 제외 최대값) + 1`을 계산한다. 그 값을 변수에 담아 `insertList`가 그대로 보낸다. 그래서 낙관적 값과 서버 값이 같고, 동기화 뒤 재조회해도 순서가 흔들리지 않는다. 마이그레이션은 필요 없다. 두 기기가 오프라인에서 같은 값을 만들 수도 있는데, 그때는 생성 순으로 정렬해도 괜찮다(드문 경우이고, 다음에 순서를 바꾸면 정리된다).
3. **큐와 순서 바꾸기.** 순서를 바꿀 때마다 별도의 큐 항목이 되고, 큐 순서대로 적용되어 마지막 것이 이긴다. 합치지 않는다. 낙관적 재정렬은 캐시에 있는 목록 전부(오프라인에서 만든 목록 포함)를 대상으로 한다. 오프라인에서 만든 목록은 같은 큐에서 먼저 만들어지므로 RPC 때 이미 존재한다.
4. **Realtime.** 기존 `src/realtime/apply-change.ts`는 재조회를 1초 debounce(최대 3초)로 묶고, 큐가 비어 있지 않으면 미룬다. RPC 하나가 만드는 UPDATE 이벤트 N개는 재조회 한 번으로 모인다. 그래서 따로 손대지 않는다.
5. **스크롤과 제스처 루트.** 홈에는 지금 당겨서 새로고침이 없으므로 `ReorderableList`로 바꿔도 잃는 동작이 없다. `GestureHandlerRootView`는 이미 루트(`app/_layout.tsx`)에 있다.
6. **항목 줄 누르기.** 메모가 있든 이름이 길든 줄을 누르면 완료/해제된다. 연필 아이콘은 스와이프 행 안에 함께 둔다. 선택 모드에서는 지금처럼 누르면 선택/해제되고, 연필은 숨긴다.
7. **DB 타입과 권한.** `src/lib/database.types.ts`는 생성된 파일이다. 로컬 Supabase에서 마이그레이션을 적용한 뒤 `npx supabase gen types typescript --local`로 다시 만든다. 다시 만든 결과가 기존 파일 형식과 크게 다르면 RPC 시그니처만 손으로 추가한다. `reorder_lists`의 실행 권한은 `0003_rpc.sql`과 같은 방식으로, public·anon에서는 회수하고 authenticated에만 준다.

## 테스트

- 리스트 순서: 순수 함수(놓은 결과 → ids, 낙관적 재매김), mutation(변수·낙관적·롤백), 홈 화면에서 `onReorder` 콜백을 호출했을 때 mutation이 올바른 ids로 불리는지. 라이브러리 제스처 자체는 Jest 목으로 대신하고 시뮬레이터에서 확인한다.
- DB: `reorder_lists` pgTAP.
- 항목 누르기·헤더 아이콘·유형 표시: 화면 테스트.

## 확인

Expo Go(iOS 시뮬레이터)에서 확인할 것:
- 길게 눌러 끌기, 짧게 눌러 이동, 스크롤과 충돌 없음
- 다른 기기 화면 반영(두 번째 시뮬레이터로)
- 항목 줄 누르기로 완료, 연필로 편집

Metro는 변경 후 `--clear`로 다시 시작해야 반영된다(이 개발 환경 특성).

- 아이콘과 이름 사이 간격 등 세부 스타일
